# 安装应用单一会话审计（2026-08-28）

## 1. 审计目标与范围

本审计针对真实车机复测中出现的两类误报：

1. 03投屏已写入车机、授权页正常，但助手显示授权失败。
2. 文件管理器已写入车机、授权页显示四个应用均正常，但助手显示安装失败。

审计范围锁定安装应用主链，不扩展到维护首页的独立动作：

1. `InstallationSession` 的批次、证据、事件和终态。
2. `DeviceInstallationCoordinator` 的安装、授权、可用性编排。
3. `AdbCommandGateway` / `DadbCommandGateway` 的 PackageManager 回执、身份回读和授权回读。
4. `InstallerRuntime` / `ProductionInstallerRuntimeFactory` 的生产路径与历史兼容入口。
5. `InstallUiStateMapper` / 结果行的终态投影。
6. 现有单测、回归夹具、Debug/设备验证入口。

不在本轮范围内：下载源协议、APK 发布者身份本身、维护应用管理的卸载/启动动作、视觉动效。除非这些边界直接改变安装批次终态，否则只记录为依赖。

5. 该证据揭示审计时代码的长期私有副本保留与产品 / 架构文档“已校验 APK 持久保留在公共 `Download`”之间存在口径差异。本节只记录当时事实；该策略差异已在第 11 节完成收口，当前实现以第 11 节为准。

## 3. 施工前结果裁决链

审计取证时安装动作的实际路径如下：

```text
PreparedArtifact
  -> DadbCommandGateway.install (逐组件)
  -> DeviceInstallResult
  -> DeviceInstallationCoordinator 中间分类
       -> ComponentFailed*（可能多次）
       -> InstallationCompleted
       -> AuthorizationCompleted
       -> ComponentFailed*（授权/验证阶段）
       -> DeviceVerified
  -> InstallationSession 逐事件更新 evidence/failed ids/state
  -> InstallationSessionSnapshot.resolveInstallationResult 再汇总
  -> InstallUiStateMapper 再选文案与结果页状态
```

这条链的关键不变量没有成立：

1. 一个组件可以同时拥有 `installed=true` 和 `failedComponentIds` 成员。
2. 一个组件的安装阶段失败、授权阶段失败、可用性阶段失败没有独立的不可覆盖槽位。
3. 一个批次没有不可变的“每组件唯一终态收据”；终态由事件顺序和多个集合的交集推导。
4. 设备层的命令成功、回读未知、身份不匹配和后置授权失败没有统一的批次级封装。

## 4. 根因候选与反例

### R-01：后置授权回读把真实授权成功降级为授权失败

触发条件：设备命令已经写入授权并输出完整 marker，但独立 `readAuthorizationPostcondition()` 因 Android 9 读取延迟、格式差异或某一个 action 暂时未知返回 `NotSatisfied/Unavailable`。

可观察结果：车机授权页正常，助手收到 `DeviceShortcutResult.Failed`；协调器把未得到完整 receipt 的组件写入 `failedComponentIds`，结果页显示授权失败。

证据：E-04、E-05、E-10、T-04。

### R-02：文件管理器逐 action 回读的一个失败污染整组件安装结果

触发条件：文件管理器的 5 个授权 action 中有一个 `dumpsys package`/AppOps 读回暂时未知，或命令 marker 已完整但二次读取不稳定。

可观察结果：PackageManager 已安装，车机授权页显示全部正常，助手仍以 `AuthorizationAttempt.Failure` 记录组件失败；由于失败集合和安装证据共用，最终可能显示“安装失败”。

证据：E-04、E-05、E-06、E-10、T-04。

### R-03：03投屏零动作语义在协调器层丢失

触发条件：cast plan 无 action；设备层可以返回空 evidence + configured cast，但协调器仍按“桌面存在、候选已配置、验证 evidence”路径处理，或使用旧固定脚本/选中集合判断。

可观察结果：cast 已安装且不需要授权，但客户端把“没有授权 evidence”当成未配置或授权失败。

证据：E-11、E-13；现有测试只覆盖 factory 层零 action，不覆盖生产协调器到 UI 的完整路径。

### R-04：安装身份回读失败被当成安装失败，而设备写入已成功

触发条件：`pm install -r` 成功后 `pm path`、pull 或 metadata 回读暂时失败；或厂商 split 路径不满足严格 parser。

可观察结果：车机包已存在，助手收到 `WrittenButUnverified`。当前设计虽有 pending 类型，但后续批次仍可能因为 desktop prerequisite / authorization candidate 缺失而发出额外失败事件。

证据：E-09、E-12、T-02。

### R-05：多 callback/多裁决路径导致生产与测试语义漂移

触发条件：生产使用 batch callback，历史或恢复路径使用 strategy/flow/legacy callback；某一路径对缺失 artifact、复用组件或失败事件处理不同。

可观察结果：同一设备状态在不同入口显示不同结果，修复一条路径后另一条路径继续误报。

证据：E-14、E-15。

1. 当前没有证据证明车机实际没有安装；用户复测反而证明两个包都已写入。
2. 当前没有证据证明文件管理器 APK 包名或发布者证书错误；这类明确身份不匹配应继续保留为真正安装失败。
3. 当前没有证据证明维护本地基线保存失败导致本次 UI 误报；该副作用按设计不应回写会话结论。
4. 车机离线，无法判断具体是哪一个 Android 9 命令输出触发 R-01/R-02；必须通过 fake 组合测试和设备复测分别确认。

## 6. 策略冻结前的必须满足条件

1. 设备层一次调用返回一个不可变 `InstallationBatchReceipt`，包含每组件唯一的安装事实、授权事实、可用性事实、待确认事实和结构化原因；不得再靠调用方从多个结果集合拼装。
2. `InstallationSession` 只接受一个批次完成事件（进度事件除外），由唯一 owner 一次性写入终态；旧的三段终态事件不能继续作为生产主链。
3. 每组件终态按严格优先级裁决：
   - 身份明确不匹配 -> `INSTALLATION_FAILED`；
   - 写入成功但身份暂时未知 -> `INSTALLATION_PENDING_CONFIRMATION`；
   - 身份已确认但授权未满足/未知 -> `AUTHORIZATION_INCOMPLETE`；
   - 授权已确认但可用性未满足 -> `AVAILABILITY_INCOMPLETE`；
   - 安装、授权、可用性均满足 -> `READY`。
4. 后置失败不能把已确认安装降级为“未安装”；失败阶段必须独立保存。
5. 零 action 组件的授权事实必须是显式 `NOT_REQUIRED`/已配置，不得用空列表推断失败。
6. 生产只保留 batch-aware 安装入口；兼容入口只能在测试适配层保留，不能进入生产组合根。
7. UI 只读取会话已经裁决好的 `InstallationResultSummary`，不再从 raw evidence、failed ids 或旧 component rows 重算。

## 7. 施工前阶段结论与施工后收口

审计已确认施工前“单一会话”只在对象存储层成立，没有在设备批次收据和终态裁决层成立。R-01/R-02 是最符合用户现场现象的高概率根因，R-03/R-04 是必须同时覆盖的边界，R-05 是导致多轮修复反复回归的结构性原因；这些问题已由本轮第 7.1 节所述收据与唯一裁决主链处理。

## 7.1 策略冻结：单一批次收据与唯一终态裁决

以下内容是本轮施工后冻结的现行蓝图。代码、测试和文档只能实现或验证它，不能在调用点重新发明一套结果解释。

### 7.1.1 唯一物理主链

```text
InstallationBatchPlan
  -> DeviceInstallationCoordinator.executeBatch
       -> AdbCommandGateway.installBatch (一次设备批次调用)
       -> AdbCommandGateway.runShortcut (携带 typed AuthorizationPlan 的一次授权调用；同一租约内完成后置观测)
       -> InstallationBatchReceipt (不可变、每组件唯一收据)
  -> InstallationSessionEvent.InstallationBatchCompleted
  -> InstallationSession.commitBatchReceipt (唯一终态 owner)
  -> InstallationResultSummary (唯一结果投影)
  -> InstallUiStateMapper (只翻译，不重算)
```

进度事件允许在批次执行期间发送，但不得携带或修改终态事实。生产路径不再发送 `ComponentFailed` 作为批次裁决，不再以 `InstallationCompleted`、`AuthorizationCompleted`、`DeviceVerified` 三个终态事件拼装结果。

### 7.1.2 批次收据字段与不变量

`InstallationBatchReceipt` 位于 `domain/session`，由设备协调器构造、由会话一次性接收：

1. `batchId`：必须等于当前 `InstallationBatchPlan.batchId`；事件代次仍由 `AdapterEvent.sessionId/sequence/eventId` 负责去重。
2. `components`：每个 `selectedComponentIds` 恰好一项，按组件 id 去重；任何缺项、重复项、计划外 id 都拒绝整张收据。
3. 每项包含三个不可覆盖阶段槽位：`installation`、`authorization`、`availability`；每个阶段各自携带结构化 `reasonCode` / `retryable`。收据没有独立的 `failure` 槽位，失败事实必须落在实际失败阶段。
4. 安装阶段枚举：`VERIFIED`、`WRITE_CONFIRMED_PENDING_IDENTITY`、`FAILED`、`NOT_ATTEMPTED`。明确包名 / 证书不匹配只能是 `FAILED`；写入已确认但回读未知只能是 `WRITE_CONFIRMED_PENDING_IDENTITY`。
5. 授权阶段枚举：`VERIFIED`、`NOT_REQUIRED`、`UNKNOWN`、`FAILED`、`NOT_ATTEMPTED`。零 action 组件必须显式写入 `NOT_REQUIRED`；marker 已完整而二次回读暂时不可用时保留可信命令收据并标记 `UNKNOWN`，不能改写安装阶段。
6. 可用性阶段枚举：`VERIFIED`、`UNKNOWN`、`FAILED`、`NOT_REQUIRED`、`NOT_ATTEMPTED`。可用性失败只能影响可用性状态，不能清除已验证安装 / 授权。
7. 组件结果投影按 `installation` -> `authorization` -> `availability` 的阶段顺序选择第一个未满足阶段及其 `reasonCode`；`UNKNOWN` 保留为对应阶段的待确认事实，不改写已确认的更早阶段。
8. `warnings` 是非终态的清理 / 观测告警，只进入诊断和结果详情，不得改变组件状态。

### 7.1.3 唯一组件终态优先级

会话在 `commitBatchReceipt` 内对每个组件执行一次纯函数裁决，顺序固定：

1. `installation == FAILED` -> `NOT_INSTALLED`；
2. `installation == WRITE_CONFIRMED_PENDING_IDENTITY` -> `INSTALLATION_PENDING_CONFIRMATION`；
3. 安装已 `VERIFIED`，但授权为 `FAILED/UNKNOWN/NOT_ATTEMPTED` -> `AUTHORIZATION_INCOMPLETE`；
4. 安装和授权均已确认，但可用性为 `FAILED/UNKNOWN/NOT_ATTEMPTED` -> `AVAILABILITY_INCOMPLETE`；
5. 安装、授权、可用性均 `VERIFIED` 或授权为 `NOT_REQUIRED` 且可用性为 `NOT_REQUIRED` -> `READY`。

不会再通过 `failedComponentIds` 与多个 evidence 集合的交集推断终态。该集合只作为旧快照迁移 / 兼容读取字段，不是新批次的裁决输入。

### 7.1.4 生产删除与保留边界

从生产组合根删除或退出旧裁决语义：

1. `DeviceInstallationCoordinator` 的逐 APK `gateway.install(listOf(artifact))` 循环；设备层改为一个批次 API，批次内部可顺序执行但只返回一张收据。
2. `recordFailure()` 发出 `ComponentFailed` 作为终态的路径。
3. `InstallerRuntime` 的无 strategy、strategy、flow 三个旧安装 callback；生产只注入 batch callback。
4. `DadbCommandGateway.runShortcut` 中以独立 postcondition 失败覆盖完整命令 marker 的旧裁决；现行实现保留同一租约内的后置观测，但只能把暂时不可用表达为授权 `UNKNOWN`，不能抹掉命令收据。
5. UI mapper 在存在批次收据时从会话生成的 `InstallationResultSummary` 取值，不再从 raw evidence / failed 集合重算；旧快照兼容分支仍保留，仅用于没有批次收据的历史恢复。

保留并复用：

1. `InstallationBatchPlan`、官方包 / 证书校验、typed `AuthorizationPlanFactory`、连接租约、事件代次去重、进度事件、维护基线和现有安全 fail-closed 校验。
2. 旧三类事件类型及旧测试适配器可暂时保留在领域协议中，但不得由生产协调器发送；后续迁移完测试后再删除。

### 7.1.5 本轮必须通过的回归用例

1. 已有 desktop + lyrics 后，单独安装 cast（零授权 action）：批次收据明确 `authorization=NOT_REQUIRED`，最终 `READY`，不发送授权失败。
2. 已有 desktop + lyrics 后，单独安装 file-manager（五个 action）：五项 marker 完整即授权成功；独立回读短时未知只能得到授权 `UNKNOWN` / 待确认，不得变成安装失败；最终设备状态已安装时不得显示 `NOT_INSTALLED`。
3. 命令 marker 成功、postcondition 读取暂时不可用：安装保持 `VERIFIED`，授权保持 `UNKNOWN`，结果为 `AUTHORIZATION_INCOMPLETE` 或明确待确认，不得清除安装证据。
4. 设备写入成功、身份回读未知：仅 `INSTALLATION_PENDING_CONFIRMATION`，不得进入授权调用。
5. 包名 / 证书明确不匹配：`NOT_INSTALLED`，并保留具体 reason code。
6. 连续两个 batch 的旧事件 / 旧收据：sessionId 或 batchId 不匹配时完全丢弃，不污染新批次。
7. 后置授权 / 可用性失败：组件仍保留 `installed=true`，只能显示 `AUTHORIZATION_INCOMPLETE` / `AVAILABILITY_INCOMPLETE`。
8. UI mapper 对同一 `InstallationResultSummary` 只做文案翻译；构造互相矛盾的旧 raw 字段不能改变新收据裁决。

## 11. 2026-08-29 APK 来源策略施工后收口

本节覆盖第 2.4 节所记录的旧版本私有 APK 复用问题；第 2.4 节保留为 2026-08-28 审计时的历史源码和设备证据，不代表当前实现。

1. 当前跨会话 APK 来源只有手机公共 `Download` / Android Q+ 的 `MediaStore.Downloads`。候选仍必须通过包名、版本、发布者证书、大小和 SHA-256 校验；公共候选未命中后才进入声明 ZIP 的远端获取、校验、解压和公共目录发布。
2. `ArtifactCache` 已移除 `verified-apks` 的创建、扫描、读取和保留逻辑。私有 `cacheDir/install-artifacts` 只保存当前操作的 ZIP 断点、解压临时 APK 和 MediaStore 读取副本；安装或维护动作结束时清理整个私有工作区。
3. 应用升级后首次构造 `ArtifactCache` 会删除旧版本遗留的 `verified-apks` 目录，防止旧 APK 在用户未手动清理应用数据时继续被复用；新建或残留在私有目录中的 APK 不会进入公共候选扫描。
4. 本轮没有修改车机 `INSTALL_MISSING_ONLY` 的设备层路径。车机已安装目标包时的跳过推送仍是独立策略，不属于手机 APK 本地来源，也不改变本轮“公共 Download 优先、未命中才下载”的实现结论。
