# 03helper 项目长期总纲

## 1. 项目定位

1. `03helper` 是独立的手机 Android 应用，面向普通用户提供 03 歌词、03桌面及经过审核的可选组件安装与维护编排。
2. 首次使用只暴露连接设备、快速读取应用列表、选择组件和开始下载并安装所需的界面；安装成功后进入维护态。
3. 安装助手不承载 03 歌词或 03桌面的业务逻辑，不改变它们的包名、签名或升级链；它只通过版本化组件清单和受控设备端口协作。
4. 前置分发默认只安装助手本体；组件由助手按 Cloud schema V4 签名配置获取，Debug / staging 兼容读取没有 Logo 的 v3 历史快照，Release production 只接受 v4。配置只下发一个受保护的蓝奏密码根文件夹、`apps[]` 动态目录声明、`versionCode`、`versionName`、`apkSizeBytes`、展示信息、安装策略、受限的 typed `deviceSetup` 和用于发布校验的 `icon` 元数据；选择页直接显示规范化版本 / 体积，`catalogVersion` 只作内部修订。包名、证书和最低 SDK 不由网络覆盖，而是从 APK 读取并用客户端内置官方发布者证书根校验。初始化使用内置最新 Logo，用户确认后先复用公共 `Download` 中匹配 APK，验签后从 APK 读取图标并按组件、版本和 APK 摘要缓存，再处理未命中的 ZIP。运行时不得请求远程 Logo。production 公钥和 Release 产物已完成本地核验，但真实蓝奏入口、文件完整性、Logo 公网对象与线上配置仍待 Cloud 发布。
5. 任何未完成实证的下载源、OTG 能力、系统授权或车机私有接口均记录为待验证，不写成正式能力。

## 2. 物理主链与 owner

### 2.1 已落地的 F0/F1 工程基座

1. Android 工程为单 `app` 模块；`applicationId` 与 `namespace` 均为 `com.ninepointnine.helper`，沿用 03 桌面和 03 歌词的 `com.ninepointnine` 组织前缀，同时保留 `helper` 独立包身份。Debug / staging 继续使用 `versionCode=1`、`versionName=0.1.0`；当前 Release 真值为 `1.0.2` / `versionCode=3`。
2. 手机端采用现代 Android 基线：JDK 17、Gradle 8.11.1、Android Gradle Plugin 8.9.2、Kotlin / Compose plugin 2.1.0、`compileSdk/targetSdk=36`、`minSdk=26`。03 歌词和 03桌面仍以 Android 9 车机为运行目标；该限制不下沉为安装助手手机端的 `targetSdk`。
3. `app/src/main/kotlin/com/ninepointnine/helper/domain/session/InstallationSessionState.kt`、`InstallationSessionSnapshot.kt`、`InstallationSessionCommand.kt` 与 `InstallationSession.kt` 定义并拥有唯一会话主链；快照包含会话代次、修订号、可恢复检查点和结构化证据，外部能力仍通过后续端口注入。
4. `app/src/main/kotlin/com/ninepointnine/helper/ui/state/InstallUiStateMapper.kt` 是领域快照到首次安装 / 维护界面的唯一投影；`InstallApp.kt` 只消费该投影、拥有维护二级页路由并分发 `InstallUiIntent`，页面不得直接持有 ADB、WebView、下载协议或第二套状态机。
5. `app/src/main/kotlin/com/ninepointnine/helper/ui/theme/` 统一拥有颜色、尺寸、文字与非线性动效令牌；`ui/components/` 统一拥有 Lucide 图标解析、按压反馈、步骤指示和错峰进入；`ui/screens/` 负责首次安装壳、维护首页和维护动作 / 安装结果二级页呈现。
6. `app/src/debug/kotlin/com/ninepointnine/helper/debug/DebugScenarioActivity.kt` 提供确定性的 fake command / adapter event 场景，只存在于 Debug 变体，不进入 Release 清单；生产 `MainActivity` 创建同一个 `InstallationSession` 并以生命周期感知方式收集快照，不再硬编码静态 `IDLE` 快照入口。
7. F0 主源码清单不申请网络、存储、ADB、WebView、无障碍或其它业务权限；AndroidX 合并清单自动生成的签名级动态接收器权限属于框架产物，不代表助手获得业务能力。后续能力必须在对应阶段通过端口、适配器和最小权限评审后进入。

### 2.1.1 Android 身份与发布版本

1. `com.ninepointnine.helper` 是 03helper 唯一 Android 身份；历史 `com.tcrrry.helper` 只保留在进度审计中，不得继续构建或作为升级目标。

Release production distribution-config 固定信任 `03helper-production-config-2026-08-30-v1` 的 P-256 公钥，SPKI DER SHA-256 为 `a971be7085a2a4a3ef8df8dd2b9df5a94b46e05b3ce85b934ffc84e42ce70051`；只接受 schema v4、`SHA256withECDSA`、`environment=production` 和 `channel=release`。该公钥不是 APK production 证书，未知 keyId 或 staging / Debug 材料不得回退接受。

### 2.3 安装批次、事件代次与设备证据边界

1. `app/src/main/kotlin/com/ninepointnine/helper/domain/session/InstallationBatchPlan.kt` 的 `InstallationBatchPlan` 在用户确认选择后冻结一次业务安装尝试。`batchId` 只表示这次尝试；`InstallationSessionSnapshot.sessionId` 和 `InstallationSessionCommand.AdapterEvent.sessionId` 表示适配器事件代次。断线恢复、已知端点重连和检查点恢复只推进事件代次并保留原批次；只有用户开始新的业务尝试才创建新的批次。适配器事件必须同时匹配当前 `sessionId`、单调 `sequence` 和去重用 `eventId`，任何一项不符都不能改变会话。
2. `app/src/main/kotlin/com/ninepointnine/helper/data/web/FolderEntrySnapshotStabilizer.kt` 的 `FolderEntrySnapshotStabilizer` 对渐进 WebView DOM 读取做规范化、去重和累积。`observe` 在签名配置声明的目标 ZIP 尚未全部出现时只能返回 `Wait`，中间快照不得宣布某个 APP 缺失；只有既有有界截止点 `completeAtDeadline` 才能固化最后快照。`LanzouFolderSourceAdapter` 默认总超时为 `30_000ms`，`AndroidLanzouWebViewHost` 另有 `48` 次、每次 `200ms` 的触发保护。截止时有非空累积快照才进入逐 APP 匹配，空快照仍返回目录解析超时。
3. `InstallationBatchPlan.resultComponentIds` 是当前结果页的唯一组件集合，等于 `selectedComponentIds - reusableComponentIds`。`InstallationSession` 的结果聚合和 `InstallUiStateMapper` 只能读取该集合；上一批失败、完整控制面清单、维护基线或临时准备清单都不得注入当前结果行。可复用的维护应用只作为当前批次的内部安装 / 授权前置证据，不伪装成这次新安装的结果。
4. 手机本地维护基线是 `InstallerRuntime` 管理的外部副作用，不属于 `InstallationSessionSnapshot`，也不参与安装、授权或可用性结果裁决。运行时只在会话产生已验证安装身份后保存必要基线；保存失败只记录诊断日志，不生成用户可见状态、不回写领域结论，也不能触发反馈循环。下次启动或维护重连必须以车机实时库存重新确认状态。
5. `app/src/main/kotlin/com/ninepointnine/helper/data/device/DadbCommandGateway.kt::BoundServiceEvidenceParser` 同时接受 `package/full.ClassName` 和 Android 9 `dumpsys` 常见的 `package/.ShortClassName` 两种拼写，并只在同一服务记录窗口（`4_096` 字符）内看到 `hasBound=true` 才返回绑定证据。原始 `dumpsys` 文本留在适配器边界，领域和 UI 只消费结构化结果；该兼容性以当前 `S56_HQX` Android 9 实测为依据，不外推为所有厂商实现。
6. `InstallationSessionEventDispatcher.isBatchActive(batchId)` 是设备批次写入前后的活动门禁：同时要求事件代次仍匹配、会话仍处于 `INSTALLING`、批次号仍匹配且尚未提交收据。`DeviceInstallationCoordinator.executeBatch` 在首次设备写入前、设备调用返回后、后置授权返回后和终态收据发送前检查该门禁；非协作式 ADB 调用无法在检查后立刻中断时，返回结果会被丢弃，不得进入授权或会话提交。
7. `InstallationBatchReceipt.validationFailure` 按组件独立构造 `AuthorizationPlanFactory.createForManifests(listOf(manifest), requireDesktop = false)`。可选组件 setup 被拒绝时只能以带原因的 `FAILED` / `UNKNOWN` / `NOT_ATTEMPTED` 落账且不得携带 evidence；其它组件仍按自己的合法计划校验并提交，不能被全局计划污染。可复用组件仍必须通过合法计划和 `PRESERVED` 基线校验。

## 3. 安装会话状态

安装会话至少区分 `IDLE`、`DISCOVERING`、`CONNECTING`、`CONNECTED`、`SELECTION_CONFIRMED`、`PREPARING_ARTIFACTS`、`ARTIFACTS_READY`、`INSTALLING`、`AUTHORIZING`、`VERIFYING_DEVICE`、`SUCCEEDED`、`COMPLETED_WITH_ERRORS`、`PAUSED`、`FAILED` 和 `MAINTENANCE`。每个状态必须有进入原因、可执行动作、取消语义和恢复策略；获取、检查、发送、授权、检查可用性五个用户阶段只是 UI 投影，不再拆成独立领域状态；未知状态只能停在安全失败态。

首次安装的用户边界固定为：

1. 用户动作只发生在“连接设备”和“选择应用（含开始下载并安装确认）”；发现后的连接握手、配置 / 根目录轻量读取、用户确认后的下载页解析、ZIP 下载与校验、APK 解压与校验、ZIP 删除、按服务端 `apps[]` 和 `sortOrder` 生成的已选应用批量非流式推送与安装、一次动态授权计划、仅 03 桌面启动和快速验证由会话及应用适配器自动推进。
2. `CONNECTING` 只表示用户已选定候选且正在执行第二次真实 ADB 握手；只有 `DeviceConnectionConfirmed` 事件到达后才能进入 `CONNECTED`。`CONNECTED` 必须保存结构化设备身份、能力和应用层连接租约，不能因为端口可达就推断 OTG、无线调试开关或其它系统权限已可用。
3. `CONNECTED` 阶段清单加载失败只表示安装资料不可用：必须保留已确认设备、记录结构化原因并清除安装检查点，不能转成 `FAILED` 或显示可继续安装进度；用户只能从选择页重新获取清单。
4. `MainActivity.onResume` 是唯一前台恢复入口，首次进入或重新回到前台（包含锁屏覆盖后 Activity 的 `onResume`）且仍处于连接页时，应用自动派发一次有界设备发现；正在发现、连接握手、已连接选择、安装结果和维护态不重复启动扫描。持有连接租约时回到前台只做一次固定身份健康检查，不做常驻高频轮询；用户在当前前台主动停止后不立即自启。
5. 选择确认后会话进入 `PREPARING_ARTIFACTS`；协调器只通过一个带批次号的 `ArtifactBatchPrepared` 原子事件提交已准备 APK、来源和完整性证据，事件通过后会话进入 `ARTIFACTS_READY`，运行时再显式发送 `InstallationStarted` 才能进入 `INSTALLING`。安装完成事件必须携带所有已选组件从车机已安装 APK 回读得到的包名与发布者证书身份；版本、大小和 manifest SHA-256 作为实际安装观测证据保留，不重复作为 Cloud 展示字段的身份硬门禁。回读不可用的组件进入独立“安装结果待确认”，不得伪报成功或混入普通失败。随后才进入 `AUTHORIZING`，并在任何授权写入前校验 APK 权限 / Service 声明。`SUCCEEDED` 必须同时具备所有已选组件安装证据、按签名 `apps[]` 生成的版本化授权计划回读证据、03 桌面启动 / 进程 / 必要 Service 证据和其他已选组件安装存在性证据，Debug 真实组件验证也不允许走安装专用成功态。
6. 成功后状态转入 `MAINTENANCE`，维护操作复用同一会话和命令白名单，不建立第二套安装状态机。

## 4. 长期不变量

1. `desktop` 是唯一核心组件，由服务端目录声明锁定且不可在首次安装页面取消；其它启用 `apps[]` 条目按 `sortOrder` 和能力门禁动态显示，首次进入选择页默认全部选中，用户取消后才不进入本次安装。`installPolicy` 仍作为目录建议字段，不改变其它组件的可选性。
2. 安装前必须完成设备身份、组件包名、发布者证书、版本、大小和 SHA-256 校验；安装后从车机回读并核对包名与受信发布者证书，版本、大小和 SHA-256 只作为实际观测证据保留。ZIP / APK 摘要负责传输完整性和安装观测，不与 Cloud `versionCode` / `versionName` / `apkSizeBytes` 重复构成安装后身份拒绝。
3. 所有授权动作都必须是版本化白名单，执行后必须回读；未知系统值不覆盖、不猜测。
4. 新请求取消旧会话，已成功步骤可复用；断线后从最近可靠检查点恢复，不重复执行不可幂等动作。
5. UI 只依赖结构化状态，不能根据日志文本猜测成功；全部成功必须同时满足所有已选组件安装、版本化授权计划回读和 03 桌面可用性证据。单个组件失败记录到会话并跳过，最终进入部分失败结果，不阻塞其它组件。
6. 维护态的更新、重装、清理、卸载和诊断动作按风险分级，破坏性操作默认关闭并二次确认。
7. 同一安装会话最多持有一个车机连接租约；清单缺失、组件取消或进入维护态不能隐式释放租约。只有维护页的“断开车机”、用户重新发起发现、进程结束，或健康检查确认车机客观掉线时才关闭租约；其它 ADB 客户端不共享也不替代该租约。
8. 远端清单只声明已签名目录、展示信息、安装策略和受限 typed `deviceSetup`；不下发或覆盖 `packageName`、`certificateSha256`、`minAndroidSdk`，也不下发任意 shell、脚本或动态设置名。客户端用官方发布者证书根校验实际 APK 身份。
9. APK 在手机本地完成 ZIP 校验、受控解压和完整 APK 校验后才允许非流式推送；临时文件在会话结束或取消后按生命周期清理。
10. 首次安装和维护态共享蓝色整屏背景，用户可见状态只能通过统一的非线性动效令牌切换；页面、按钮、进度和结果不得各自复制或绕过第二套动画参数。
11. `INSTALL_MISSING_ONLY` 的设备写入前必须完成一次可信包库存读取；只有库存中的目标包名与受信 manifest `versionCode` 精确匹配时才跳过推送和 `pm install -r`，仍须完成 APK 包名 / 发布者证书回读。旧版或版本未知的目标包必须走已校验 APK 的安装路径；只有显式 `REINSTALL_SELECTED` 才允许对精确匹配包覆盖安装。
12. 控制面目录、车机实时库存、已安装基线 manifest 和当前批次准备 manifest 不得互相以“列表非空”代替；控制面刷新必须使旧批次回到未准备状态，已安装基线只能在库存 `READY` 且包身份 / `versionCode` 完全匹配时参与跳过决策。库存只证明存在但缺少版本或受信身份时，UI 仍显示“已安装”且不渲染勾选框；会话 owner 必须把该组件加入内部核验批次，不能静默排除。
13. 业务批次 `batchId` 与适配器事件代次 `sessionId` 永远不可互相推导。重连或恢复产生新事件代次但继续消费原 `InstallationBatchPlan`；新批次必须重新冻结选择、可复用集合、准备集合和结果集合。迟到的旧代次事件即使内容看似成功也必须丢弃。
14. 渐进目录解析只能在目标 ZIP 全部可见或有界截止点到达时定案；截止点前不得把局部 DOM 当作“下载目录中没有应用”。默认 30 秒外层超时和 WebView 48 次 x 200ms 触发保护是现行边界，空快照才是整体解析超时，非空不完整快照由逐 APP 匹配产生局部失败。
15. 当前批次结果必须与历史结果和维护库存隔离。结果行只来自 `InstallationBatchPlan.resultComponentIds`，失败原因只绑定当前批次 / 当前事件代次；维护基线中的已安装应用不能覆盖当前缺失应用的结果，也不能把上一批失败复制到下一批。
16. 手机本地维护基线保存是 `InstallerRuntime` 的外部副作用，不进入领域快照和 UI 状态。只保存已验证安装身份；保存失败只写诊断日志，不能改变安装、授权、可用性或车机库存结论，也不能因为状态投影重复保存同一基线。下次启动必须通过车机实时库存重新建立可用状态。
17. Android 9 目标车机的 Service 可用性验证必须通过结构化解析同时覆盖完整组件名和 `package/.ShortClassName` 缩写；只有 `hasBound=true` 的同一记录才算绑定成功。不得在 shell、页面或日志分支中另写一套字符串匹配，也不得把原始 `dumpsys` 输出当作领域成功条件。
18. 安装结果分类必须集中在 `DeviceInstallationCoordinator.classifyInstallationResult`：明确身份不匹配或设备写入 / 前置校验失败永远是 `FAILED`；已确认操作但仅安装身份回读失败（`installation_package_path_missing`、`installation_installed_apk_*`）才是 `WRITE_CONFIRMED_PENDING_IDENTITY`；有效身份 evidence 不能被普通后续 readback 噪声抹掉。`isInstallAccepted` 对非零退出码只接受独立、明确的 `Success` 行，且任何 failure marker 优先拒绝。
19. `CombinedAuthorizationCommand` 只有在所有内置组件仍使用静态脚本支持的 canonical package identity 时才允许走静态分支；desktop、lyrics 或 file-manager 的 staging / 其它受信别名一旦出现，必须使用 `--dynamic` 和该计划的 typed action token，禁止套用旧硬编码包名。
20. `MaintenanceController.inspectApplications` 必须把受控库存与 `ThirdPartyApplicationStatus` 分开读取并在 `InstallUiStateMapper.maintenanceApplicationRows` 合并为一张平铺清单；第三方来源只允许 `/data/app/.../base.apk`，按 `firstInstallTime` 降序、包名稳定排序，重复包名由受控行胜出；第三方 synthetic row 只能映射到启动、强停、卸载、详情四种固定 action，不得渗入授权、安装选择或持久化身份。

## 5. ZIP 发布物与缓存生命周期

1. `LanzouWebSourceAdapter` 必须使用 Android System WebView 默认手机端标识，在当前页面内执行正常分享页流程。下载回调归一为内存态 `ResolvedDownloadRequest`，至少携带最终 HTTPS URL、User-Agent、当次 Cookie、Referer、Content-Disposition、MIME 和页面可得的内容长度；原生下载器按需转交这些上下文，不把短时 URL 或 Cookie 写入清单、持久日志或诊断导出。
2. 每个自动应用发布物是一个单应用 ZIP：归档根目录只有一个普通 APK；ZIP 内 entry 名称由客户端实际读取并校验，不接受额外普通文件、嵌套目录、相对路径或多个 APK。
3. Cloud v3 通过 `versionCode`、`versionName`、`apkSizeBytes` 提供选择页展示和更新追踪；客户端从公共 `Download` APK 或远端 ZIP 实际读取包名、证书、版本、APK 大小和 SHA-256，安装前完整校验，安装后只用包名与受信证书裁决身份，其余字段保留为观测证据。安装后回读不可用进入待确认，包名或证书不匹配才产生身份失败；`desktop` 失败时不冻结其它组件，但最终只禁止进入维护。
4. 下载先写入应用私有缓存的 `.zip.part`。只有 ZIP 长度与摘要均通过后才允许进入解压；相同清单版本且来源支持 Range 时可恢复 `.zip.part`，其它情况删除后重新下载。
5. 解压前必须确认可用空间至少为 `archiveSizeBytes + apkSizeBytes + 64 MiB`。解压流写入 `.apk.part`，输出超过 `apkSizeBytes`、未找到预期 entry、遇到第二个普通文件或输出长度不等于 `apkSizeBytes` 时立即失败并清理。
6. APK 包名、发布者证书、版本和 SHA-256 通过安装前校验后，将 `.apk.part` 原子转为可安装 APK，并立即删除已校验 ZIP；安装完成后回读车机 APK，包名 / 证书用于身份裁决，版本 / 大小 / SHA-256 写入观测证据。解压或安装前校验失败时清理无效产物；车机回读不可用进入待确认，身份不匹配才停止该组件。
7. 已校验 APK 统一发布到手机公共 `Download` 目录并保留；公共 `Download` / `MediaStore.Downloads` 是唯一跨会话 APK 来源，安装流程只复用其中通过包名与受信证书校验的目标 APK，并保留其大小 / 哈希 / 版本证据用于更新识别。应用私有缓存只允许保存当前操作的 ZIP / 分片、解压中的 APK 和 MediaStore 临时读取副本，不得保留完整 APK 的长期副本；清理动作不得删除用户放入的其它 APK。
8. 解压使用 Android 平台自带 ZIP 能力，不要求手机文件管理器或额外解压 App；公共 `Download` 中的 APK 由维护页和系统文件管理器共同可见。
9. `ArtifactCache` 启动时清理旧版本遗留的 `verified-apks` 私有目录；`clearPrivateCache()` 清理整个应用私有安装工作区。私有目录中的任何 APK 都不参与候选扫描，只有公共 `Download` / `MediaStore.Downloads` 中的 APK 可以跨会话复用。
